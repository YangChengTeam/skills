# 智迹工单

工单用来把一件需要**别的团队**做的事情记录下来、派给对的人、并且有始有终。

一张工单的生命周期：

```
发起人提交（选定处理组）→ 组内成员认领 → 处理 → 提交验收 → 发起人确认关闭
```

派给哪个组**由你判断**：先读一遍分组列表和各组负责的范围，再决定。没有预设的类别映射表兜底，选错了就是真的派错人，所以这一步要认真。

**最关键的一条规则：处理人不能关闭自己处理的工单。** 处理人只能「提交验收」，把工单推到「待验收」，由发起人确认。这是刻意的设计，不是限制没做完——不要试图绕过它，服务端也会拒绝。

## 前置检查

工单全部走 `zhiji` 命令行，任何目录下都能用：

```bash
zhiji ticket groups      # 能列出分组就说明可用
```

报「未登录」或找不到命令时，让用户先到控制台「令牌管理」签一个个人访问令牌，然后：

```bash
zhiji login --token zj_pat_xxx
```

没装 `zhiji` 的话，「Skills 服务」页的 zhiji-setup 里有安装命令。

**不要试图自己去读数据库或直接调 HTTP 接口**，也不要伪造工单号。

你的身份由令牌决定，命令和工具都不需要、也不能指定「我是谁」。

## 一、帮用户提工单

当用户想让别人做某件事——配域名、开账号、申请资源、要一台机器——走这里。

1. **先看有哪些分组。**

   ```bash
   zhiji ticket groups
   ```

   输出里每个组都带「负责范围」。**你要根据这些说明判断这件事该派给谁** —— 这是你的职责，不要跳过。

2. **把你选的组念给用户确认**，特别是当有多个组看起来都沾边、或者说明里没有明确覆盖这件事的时候。拿不准就问，不要随便挑一个。

3. **写清楚再提交。** 标题一句话说明要做什么；`--body` 里写：
   - 背景：为什么需要这个
   - 具体要求：域名是什么、指向哪里、什么规格
   - 验收标准：怎样算做完了

4. 提交：

   ```bash
   zhiji ticket new --group ops \
     --title "配置 zhiji.example.com 域名" \
     --body "需要解析到 10.0.1.20，签发证书并配置自动续期。验收：访问 https://zhiji.example.com 返回 200。" \
     --priority high
   ```

   `--group` 可以传分组标识、名称或 ID。传错会直接报错并列出现有标识，不会随便派给某个组。

5. 把返回的工单号和处理组告诉用户。

优先级默认 `normal`。只有真正阻塞生产、影响线上的才用 `urgent`——每张工单都标紧急，紧急就没有意义了。

**不要替用户编造需求细节。** 信息不足就问，比如没说域名解析到哪个地址，就问清楚再提，不要随便填一个。

## 二、处理分配给本组的工单

当用户问「有没有我要处理的工单」，或者要开始干活时：

```bash
zhiji ticket list                       # 默认只列未结束的：我发起的 + 我所在组的
zhiji ticket show tkt_xxx               # 详情 + 完整流转记录
zhiji ticket claim tkt_xxx --note "我来处理，今天内完成"
zhiji ticket update tkt_xxx --action start
zhiji ticket update tkt_xxx --action comment --note "卡在证书审批，已催"
zhiji ticket update tkt_xxx --action submit --note "已添加 A 记录…，访问 https://… 返回 200"
```

1. 先 `list` 再 `show`，搞清楚上下文再动手。
2. **先认领再干活**，别人才知道这件事有人接了；不要闷头做完才认领。
3. `submit` 的 `--note` 要写清**做了什么**和**发起人怎么验证**，例如「已在 DNS 添加 A 记录指向 10.0.1.20，证书已签发并配置自动续期，浏览器访问 https://zhiji.example.com 应返回 200」。

如果实际做的事情和工单描述不一致（比如用户要 A 但正确做法是 B），用 `comment` 说明清楚再做，不要默默改需求。

## 三、发起人验收

```bash
zhiji ticket resolve tkt_xxx --action accept --note "已确认可用"
zhiji ticket resolve tkt_xxx --action reject --note "证书没配，https 仍然报错"
zhiji ticket resolve tkt_xxx --action cancel --note "需求取消了"
```

- `accept`：确认完成，工单关闭。
- `reject`：打回。**必须写清哪里不满足要求**，否则处理人只能猜。打回后工单回到「处理中」，不是结束。
- `cancel`：这件事不用做了，撤销工单。

验收前先 `zhiji ticket show` 看处理人写的 submit 说明，按里面给的方法实际验证一下，不要不看就 accept。

## 状态含义

| 状态 | 含义 | 下一步该谁动 |
| --- | --- | --- |
| `open` | 已分配到组，等人认领 | 组内成员 |
| `claimed` | 已有人认领 | 处理人 |
| `in_progress` | 处理中 | 处理人 |
| `pending_review` | 处理人已提交，待验收 | **发起人** |
| `closed` | 已完成 | — |
| `cancelled` | 已撤销 | — |

## 排查

- **`zhiji` 命令不存在**：让用户按「Skills 服务」页 zhiji-setup 里的命令装一下。
- **报「未登录」/ 令牌无效**：到控制台「令牌管理」签个人访问令牌，再 `zhiji login --token zj_pat_xxx`。
- **提示「还没有任何分组」**：管理员还没在控制台「分组」里建组，让用户找管理员配。
- **报「找不到分组 X」**：`--group` 传错了，按提示里列出的标识重选；不要猜一个 ID 硬塞。
- **认领报 403**：你不在这张工单的处理组里。工单分配到组，不是分配给个人，不属于你的组就不该由你处理。
- **accept 报 403**：你不是发起人。处理人不能自己验收，这是刻意的。
- **操作报 409**：工单当前状态不允许这个动作，先 `zhiji ticket show` 看清楚它现在是什么状态。
- **找不到某个工单号（404）**：要么号错了，要么这张工单既不是你发起的、也不属于你所在的组。
