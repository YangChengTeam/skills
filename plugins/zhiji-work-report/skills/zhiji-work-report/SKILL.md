# 智迹工作上报

本技能驱动 `zhiji` 命令行，把当前项目的增量工作整理成一份工作日志并上报。
命令跑在本机，读取本机的 Codex / Claude Code 会话文件；只有本机能读到这些内容。

## 前置检查

需要 CLI **2.5.0 或更新版本**（完整扫描、归档支持、历史补采及技能更新）。先检查 `zhiji version`，2.3.x/2.4.x 用
`zhiji upgrade` 更新，2.2.x 及更早版本按接入技能重新下载一次。始终使用同一份客户端。

旧项目首次更新运行 `zhiji skills update --auto on`，备份并接管项目内已安装的智迹技能。
新 init 安装的技能默认受管，report 前每天自动检查一次；断网继续上报，人工修改过的
技能保留并提示。文件更新后重新读取本技能，不沿用已加载的旧指令。可用
`zhiji skills update --auto off` 关闭。此机制不修改 Codex/Claude 插件缓存。

```bash
zhiji status
```

能打印出「项目配置」那一行就说明可用。报「未登录」或「项目配置：缺失」时，按输出里的提示先
`zhiji login --token zj_pat_xxx` 或在项目根目录 `zhiji init`——**不要**替用户索要或粘贴令牌。
找不到 `zhiji` 命令的话，「Skills 服务」页的 zhiji-setup 里有安装命令。

不要试图自己去读 `~/.codex` 或 `~/.claude` 下的会话文件来代替这些命令。

## 上报流程

先采集，再判断是否有业务工作。接入操作本身不生成工作日志。

1. **采集**：

   ```bash
   zhiji report
   ```

   它打印自上次上报以来的新增会话原文摘录、Token 统计和一个 `runId`。
   - 输出「没有新增工作」时，直接告诉用户「本次没有新增工作」，**不要**编造内容去上报。

2. **筛选工作范围**：读完整批次后按语义判断，不以是否包含“智迹”等关键词判断。

   - **仅有智迹接入操作**：安装/升级 CLI、登录/令牌配置、创建接入项目、写 `.env.zhiji`、
     安装上报技能、验证接入或上报链路，不属于项目业务成果。执行：

     ```bash
     zhiji skip --run-id <上一步的 runId> --reason onboarding-only
     ```

     成功后告诉用户“本次只有智迹接入操作，已过滤，不生成工作日志”。此分支不调用
     `submit`，也不手工请求 facts/diaries；skip 只推进游标，该批次事实不会上传。
   - **接入和业务工作混合**：正常上报业务工作，总结中省略接入事项；保留完整采集事实，
     不凭猜测删除部分对话或分摊 Token。智迹产品本身的功能开发、修复、部署属于业务工作。
   - **无法确认**：输出被截断时先检查该项目 `.zhiji/run-<runId>.json` 中的完整批次。
     没有正文或只有“文档/开发工具修改了几个文件”不足以判断纯接入，不得执行 skip，
     保留批次并报告材料不足。不要为了测试接入编写一条业务日志。

   从项目外执行时，report、skip、submit 都传相同的 `--dir <项目根目录>`。

3. **上报业务工作**：自己写一份 Markdown 总结，从标准输入喂给 `submit`：

   ```bash
   zhiji submit --run-id <上一步的 runId> --completion 80 <<'EOF'
   ## 本次工作
   - 写在这里
   EOF
   ```

   - `--run-id`：上一步返回的，原样传回。
   - `--completion`：当前工作完成度百分比（0-100），按你对进度的判断给一个数。
   - 总结走标准输入，不要拼进命令行参数——多行中文 Markdown 经过 shell 引号会被改坏。

## 总结怎么写

写给同事看，不是写给模型看：

- 说清**做了什么、为什么做、结果如何**，而不是罗列你调用过哪些工具。
- 按主题分组，不要按时间流水账。改了代码就点出关键文件和行为变化。
- 保留事实：测试失败、功能未完成、被阻塞的部分都要写出来，不要只报喜。
- 用中文，控制在十几行以内；细节放在要点里。
- 不把智迹安装、登录、接入和上报验证写成项目业务成果；不要仅根据文件数量推断业务行为。

示例结构：

```markdown
## 本次工作

### 成员与项目信息支持编辑
- 新增 `PATCH /api/v1/admin/users/{id}` 与 `PATCH /api/v1/projects/{id}`
- 前端两个列表页各加了编辑弹窗

### 遗留
- 项目标识改名后旧标识不再重定向，需要确认是否有外部引用
```

## 历史补采

用户要求补传历史、找回漏采或补齐归档会话时，用 `zhiji report --history` 代替普通
report，然后仍按上述筛选及 submit 流程处理。该模式忽略正常时间游标，扫描当前机器
本项目的全部活动/归档会话，先查询服务端已有 ID，只保留缺失事实。
无缺失记录时不生成 run、不创建日志；不要重置服务器游标，也不要删除旧记录。
总结明确标注“历史补采”及实际记录时间，不能写成今天刚完成的工作。
正常增量游标保持不变；重复运行及重试不会重复插入已存在的事实。
源码与对话仍按用户已授权的上传范围处理，不能以补采名义扩大权限。

## 查询用量

用户问「本周用了多少 token」「这个月的用量」时：

```bash
zhiji usage --range week              # today / week / month / all
zhiji usage --range custom --from 2026-09-01 --to 2026-09-15
zhiji usage --range month --scope project   # 默认 member，只看自己
```

`--from` 含当天，`--to` 不含当天。回答时给出总量和模型分布，不要把原始输出整段贴给用户。

## 排查

- **报 401 / 令牌无效**：个人访问令牌被删了或过期，让用户去「令牌管理」重新签一个再 `zhiji login`。
- **报 403 不是项目成员**：让项目负责人先把用户加进项目。
- **采集为空但用户确信有工作**：`zhiji report` 的输出末尾有扫描诊断，会列出扫到的其他目录。
  确认会话确实发生在**当前项目目录**下——采集按项目根目录过滤会话。
- **上报中途失败**：输出里会写「游标未前移，可以重试」，直接用同一个 `runId` 再跑一次 `submit` 即可，
  已经上传的部分不会重复计数。
