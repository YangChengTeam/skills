# 智迹工作上报

本技能驱动 `zhiji` 命令行，把当前项目的增量工作整理成一份工作日志并上报。
命令跑在本机，读取本机的 Codex / Claude Code 会话文件；只有本机能读到这些内容。

## 前置检查

```bash
zhiji status --dir .
```

能打印出「项目配置」那一行就说明可用。报「未登录」或「项目配置：缺失」时，按输出里的提示先
`zhiji login --token zj_pat_xxx` 或在项目根目录 `zhiji init`——**不要**替用户索要或粘贴令牌。
找不到 `zhiji` 命令的话，「Skills 服务」页的 zhiji-setup 里有安装命令。

不要试图自己去读 `~/.codex` 或 `~/.claude` 下的会话文件来代替这些命令。

## 上报流程

必须按顺序走完两步，缺一不可：

1. **采集**：

   ```bash
   zhiji report --dir .
   ```

   它打印自上次上报以来的新增会话原文摘录、Token 统计和一个 `runId`。
   - 输出「没有新增工作」时，直接告诉用户「本次没有新增工作」，**不要**编造内容去上报。

2. **上报**：读完采集结果后，自己写一份 Markdown 总结，从标准输入喂给 `submit`：

   ```bash
   zhiji submit --run-id <上一步的 runId> --completion 80 <<'EOF'
   ## 本次工作
   - 写在这里
   EOF
   ```

   - `--run-id`：上一步返回的，原样传回。
   - `--completion`：当前工作完成度百分比（0-100），按你对进度的判断给一个数。
   - 总结走标准输入，不要拼进命令行参数——多行中文 Markdown 经过 shell 引号会被改坏。

## 总结怎么写

写给同事看，不是写给模型看：

- 说清**做了什么、为什么做、结果如何**，而不是罗列你调用过哪些工具。
- 按主题分组，不要按时间流水账。改了代码就点出关键文件和行为变化。
- 保留事实：测试失败、功能未完成、被阻塞的部分都要写出来，不要只报喜。
- 用中文，控制在十几行以内；细节放在要点里。

示例结构：

```markdown
## 本次工作

### 成员与项目信息支持编辑
- 新增 `PATCH /api/v1/admin/users/{id}` 与 `PATCH /api/v1/projects/{id}`
- 前端两个列表页各加了编辑弹窗

### 遗留
- 项目标识改名后旧标识不再重定向，需要确认是否有外部引用
```

## 查询用量

用户问「本周用了多少 token」「这个月的用量」时：

```bash
zhiji usage --range week              # today / week / month / all
zhiji usage --range custom --from 2026-09-01 --to 2026-09-15
zhiji usage --range month --scope project   # 默认 member，只看自己
```

`--from` 含当天，`--to` 不含当天。回答时给出总量和模型分布，不要把原始输出整段贴给用户。

## 排查

- **报 401 / 令牌无效**：个人访问令牌被删了或过期，让用户去「令牌管理」重新签一个再 `zhiji login`。
- **报 403 不是项目成员**：让项目负责人先把用户加进项目。
- **采集为空但用户确信有工作**：`zhiji report` 的输出末尾有扫描诊断，会列出扫到的其他目录。
  确认会话确实发生在**当前项目目录**下——采集按项目根目录过滤会话。
- **上报中途失败**：输出里会写「游标未前移，可以重试」，直接用同一个 `runId` 再跑一次 `submit` 即可，
  已经上传的部分不会重复计数。
