# 智迹工作上报

本技能驱动 `zhiji` MCP 服务，把当前项目的增量工作整理成一份工作日志并上报。
MCP 跑在本机，读取本机的 Codex / Claude Code 会话文件；只有本机能读到这些内容。

## 前置检查

工具名以 `zhiji_` 开头（不同宿主可能带前缀，例如 Claude Code 的 `mcp__zhiji__zhiji_report_work`；
Codex 按项目区分条目名，前缀形如 `zhiji_<项目slug>__zhiji_report_work`）。
MCP 按项目配置，所以只会看到当前项目的那一套工具；看到多套时，选条目名对应本项目的那套。
如果看不到这些工具，说明本项目还没接入 MCP：让用户到智迹「MCP 接入」页签发令牌并按页面提示配置，
然后重启会话。不要试图自己去读 `~/.codex` 或 `~/.claude` 下的会话文件来代替。

## 上报流程

必须按顺序走完两步，缺一不可：

1. **采集**：调用 `zhiji_report_work`。它返回自上次上报以来的新增会话原文摘录、Token 统计和一个 `runId`。
   - 没有新增内容时它会明确说明——这时直接告诉用户「本次没有新增工作」，**不要**编造内容去上报。
2. **上报**：读完采集结果后，自己写一份 Markdown 总结，调用 `zhiji_submit_work` 提交，参数：
   - `runId`：上一步返回的，原样传回。
   - `summary`：Markdown 总结（见下方要求）。
   - `items`：要点列表，用于列表页展示；不传会从 Markdown 自动提取。
   - `completion`：当前工作完成度百分比（0-100），按你对进度的判断给一个数。

## 总结怎么写

写给同事看，不是写给模型看：

- 说清**做了什么、为什么做、结果如何**，而不是罗列你调用过哪些工具。
- 按主题分组，不要按时间流水账。改了代码就点出关键文件和行为变化。
- 保留事实：测试失败、功能未完成、被阻塞的部分都要写出来，不要只报喜。
- 用中文，控制在十几行以内；细节放在要点里。

示例结构：

```markdown
## 本次工作

### 成员与项目信息支持编辑
- 新增 `PATCH /api/v1/admin/users/{id}` 与 `PATCH /api/v1/projects/{id}`
- 前端两个列表页各加了编辑弹窗

### 遗留
- 项目标识改名后旧标识不再重定向，需要确认是否有外部引用
```

## 查询用量

用户问「本周用了多少 token」「这个月的用量」时，调用 `zhiji_usage`：

- `range`：`today` / `week` / `month` / `all` / `custom`（`custom` 时再传 `from`、`to`，格式 `YYYY-MM-DD`，含头不含尾）。
- `scope`：`member` 只看自己，`project` 看整个项目。

回答时给出总量和模型分布，不要把原始 JSON 贴给用户。

## 排查

- 工具报未配置或 401：令牌无效或已被删除，需要重新签发。
- 采集为空但用户确信有工作：确认会话确实发生在**当前项目目录**下，MCP 按项目根目录过滤会话。
